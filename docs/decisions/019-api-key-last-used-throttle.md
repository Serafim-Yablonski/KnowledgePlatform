# 019. API Key Last-Used Time Is Best-Effort, at Five-Minute Resolution
Status: Accepted, amended by ADR-034 (authentication reads PostgreSQL; the throttle moved into `ApiKeyService`) and ADR-033 (the write has its own unit of work) | Date: 2026-10-16

## Context
`api_keys.last_used_at` lets users spot stale keys to revoke. Authentication itself was then served from Redis (`CachedApiKeyRepository.get_by_hash`, removed by ADR-034), but recording use wrote to Postgres on every MCP HTTP request, and a Streamable HTTP session sends one request per `initialize`, `tools/list` and tool call. Each write took a pool connection, a commit and a row lock on the key, so parallel calls with one key queued on that row, and the write bypassed the cache that exists to keep auth off the database. It previously ran as an unreferenced fire-and-forget task, and wrote a timezone-aware value into a naive column, which asyncpg rejects; the failure was only logged.

## Decision
After `ApiKeyService.authenticate` has read the key, it claims a Redis `SET NX EX` marker per key (`API_KEY_LAST_USED_RESOLUTION`, default 300 s) and only the claimant writes, through `touch_last_used`, using the server's `now()`. The write is awaited in its own unit of work, opened after authentication's read has closed (ADR-033), so its rollback can't touch the key and user authentication returns; its database errors are logged and swallowed, so bookkeeping can never fail authentication. If Redis is down, the claim fails closed and nothing is written: bookkeeping gives way rather than adding a write per request to a database that is already serving every auth read.

## Consequences
Database writes drop from one per request to at most one per key per five minutes, and `last_used_at` is accurate to that window, which is the resolution users need. A failed write (or a crash) after claiming the marker is not retried until the window ends, deliberately: during a database outage each key costs one failed attempt per window, not one per request. `last_used_at` also stops advancing while Redis is down. **Rejected: a conditional `UPDATE … WHERE last_used_at < now() - interval`**: it avoids most row writes but still costs a database round trip per request. **Rejected: buffering in Redis and flushing from Celery beat**: a scheduler and flush job for one timestamp. **Rejected: dropping the column**: users rely on it to find unused keys. **Rejected: a SAVEPOINT around the write** to keep the rollback from expiring loaded objects: it relies on SQLAlchemy subtleties (the ORM `UPDATE` synchronises the identity map; a failed `commit` after the savepoint is still a full rollback), while a separate session (before ADR-033, a detached snapshot from the cache) is immune to anything the write does.
