# 019. API Key Last-Used Time Is Best-Effort, at Five-Minute Resolution
Status: Accepted | Date: 2026-10-16

## Context
`api_keys.last_used_at` lets users spot stale keys to revoke. Authentication itself is served from Redis (`CachedApiKeyRepository.get_by_hash`), but recording use wrote to Postgres on every MCP HTTP request, and a Streamable HTTP session sends one request per `initialize`, `tools/list` and tool call. Each write took a pool connection, a commit and a row lock on the key, so parallel calls with one key queued on that row, and the write bypassed the cache that exists to keep auth off the database. It previously ran as an unreferenced fire-and-forget task, and wrote a timezone-aware value into a naive column, which asyncpg rejects; the failure was only logged.

## Decision
`ApiKeyService.authenticate` records use through `touch_last_used`, which `CachedApiKeyRepository` throttles with a Redis `SET NX EX` marker per key (`API_KEY_LAST_USED_RESOLUTION`, default 300 s). Only the first request in each window writes, using the server's `now()`. The write is awaited, but its errors are logged and swallowed, and the repository rolls back on failure, so bookkeeping can never fail authentication or poison the session. That rollback expires every object the session holds, so the key and user that authentication returns must not be held by it: `ResponseCache.get_or_set` returns the deserialized copy on a miss as well as on a hit, so a cached read always yields a detached snapshot. If Redis is down, the claim fails closed and nothing is written: bookkeeping gives way rather than adding a write per request to a database that is already serving every auth read.

## Consequences
Database writes drop from one per request to at most one per key per five minutes, and `last_used_at` is accurate to that window, which is the resolution users need. A failed write (or a crash) after claiming the marker is not retried until the window ends, deliberately: during a database outage each key costs one failed attempt per window, not one per request. `last_used_at` also stops advancing while Redis is down. **Rejected: a conditional `UPDATE … WHERE last_used_at < now() - interval`**: it avoids most row writes but still costs a database round trip per request. **Rejected: buffering in Redis and flushing from Celery beat**: a scheduler and flush job for one timestamp. **Rejected: dropping the column**: users rely on it to find unused keys. **Rejected: a SAVEPOINT around the write** to keep the rollback from expiring loaded objects: it relies on SQLAlchemy subtleties (the ORM `UPDATE` synchronises the identity map; a failed `commit` after the savepoint is still a full rollback), while a snapshot is immune to anything the session does later.
