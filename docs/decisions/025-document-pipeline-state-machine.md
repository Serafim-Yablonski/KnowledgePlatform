# 025. The Document Pipeline Is a Guarded State Machine; the Phase Decides Retries
Status: Accepted | Date: 2026-10-24 | Amended 2026-10-25 (an OOM kill is an attempt, `extraction_too_large`) | Amended by ADR-027 (2026-11-02): the state machine, the guarded writes and the phase's retry rule hold; Celery's mechanics (autoretry, `on_failure`, the hand-off message) are replaced by the work-queue runner

## Context
An upload moves `PENDING` → `PROCESSING` (`extract_text`) → `READY` → `INDEXED` (`embed_chunks`), and the pipeline's requirement is that every upload ends `INDEXED` or `FAILED` without operator action. Before this decision, many failures a worker could see left a document non-terminal for good, because an uncaught exception fails a Celery task with its message acked and the status unchanged. pypdf raises an open set of exceptions beyond `PdfReadError` (`KeyError`, `ValueError`, `LimitReachedError`…): 18 % of 3,000 byte-mutated PDFs on 6.10.2, still 0.5 % on 6.21.2. A scanned PDF or a whitespace-only file chunked to nothing and stayed `READY`. A NUL or a lone surrogate in pypdf's output failed at the save. Extraction wrote `FAILED` before every retry, so a document that might still succeed already read as failed, and `FAILED` never said why. Every status write was an unconditional update of a row read earlier, so a losing concurrent run's `FAILED` could overwrite a winner's `INDEXED`. Concurrent runs are rare today (Redis redelivers an unacked message only after an hour) but become ordinary once a reconciler requeues work. Two facts ruled out the in-process fixes. First, Celery's soft time limit is a plain `Exception` raised from a signal handler, and pypdf's broad `except` sites swallowed it in 15 of 300 probes on 6.21.2, 3 of them returning text with about 2.5 k characters missing. Second, Celery pickles the final exception before `on_failure` sees it and rebuilds it as `cls(*args)`.

## Decision
**Guarded transitions.** The workers' status writes form a table in `domain/documents.py`. Each entry is a `Transition(to, allowed_from)`, applied as one `UPDATE … WHERE status IN (allowed_from)` (`workers/transitions.py`). An UPDATE that waited on a concurrent writer's row lock re-checks its `WHERE` against the committed row, so the check and the write are one step. Extraction claims from `PENDING`/`PROCESSING`, saves `READY` from `PROCESSING` and fails from `PENDING`/`PROCESSING`. Embedding fails only from `READY`. The chunk swap sets `INDEXED` from any status, under the row lock. So each task fails only the stage it owns, no run starts on `FAILED`, and a run already under way may still finish `INDEXED`: a success beats a failure. **The phase decides retries, not the exception type.** Pure phases (parsing bytes already read, chunking stored text) raise `PermanentFailure(reason)` and are not retried. Everything that touches the outside world (file, database, broker, embedding API) is retried by Celery's native autoretry on the shared base `PipelineTask`: `autoretry_for=(Exception,)`, `dont_autoretry_for=(PermanentFailure,)`, three retries, backoff doubling from 30 s (extraction) or 60 s (embedding), full jitter. Between attempts the document keeps its status. When no attempt remains, `on_failure` writes the task's own `FAILED` transition with a reason. **Reasons.** `failure_reason` is a nullable enum column with a CHECK that allows it only on `FAILED`, and the swap clears it. Four reasons are the file's (another upload can fix them): `no_text`, `unreadable_file`, `extraction_timeout`, `extraction_too_large`. Two are ours: `embedding_failed`, `internal_error`. REST and MCP expose the reason, and `read_document` gives each reason its own detail. **The PDF parse runs in a child process**, `src/workers/pdf_text.py`. It runs by path under `python -I`, because the image puts `src` on `PYTHONPATH`, which `-I` ignores. The parent reads the file (I/O, retried) and pipes the bytes in. Exit 0 means text. The child's parse-failed code, or a crash (death by a signal other than SIGKILL), means `unreadable_file`: the same bytes repeat it. A kill at `CELERY_EXTRACT_PARSE_TIMEOUT` means `extraction_timeout`. Any other SIGKILL is the OOM killer under the extract container's memory cap (`mem_limit` = `memswap_limit`, so it kills instead of swapping). Its victim is the biggest process at that instant, which depends on what else is parsing, so it is an attempt, not a verdict: `ParseKilled` is retried, and a parse killed on every attempt ends `extraction_too_large`. This is how production parsers are bounded: a kill plus an attempt count. Any other exit (e.g. a broken deploy) is retried, then becomes `internal_error`. A settings validator keeps parse timeout < soft limit < hard limit; the soft limit stays a backstop for the other phases. The child replaces NUL and unpaired surrogates with U+FFFD, using a UTF-16 `surrogatepass` round trip that rejoins a character pypdf split into two halves. "No text" means the chunker returned no chunks, decided in `embed_chunks`. Pinned by:
- transitions: `test_no_run_starts_on_a_failed_document`, `test_a_failed_extraction_never_overwrites_a_rivals_ready`, `test_a_losing_runs_failure_never_overwrites_a_winners_indexed`, `test_a_failure_write_waiting_on_a_swap_rechecks_and_changes_nothing`, `test_a_run_under_way_still_finishes_indexed_over_a_rivals_failed`;
- retries: `test_a_file_that_stays_unreadable_fails_after_the_retries`, `test_embed_chunks_sets_failed_when_retries_exhausted`, `test_a_file_that_cannot_be_parsed_fails_at_once_as_unreadable`, `test_a_chunking_failure_fails_at_once_without_embedding`, `test_pipeline_tasks_retry_through_celerys_autoretry`;

## Consequences
Every failure a worker observes now ends terminal, with a reason a client can act on. A corrupt file fails in one attempt instead of four, and a text-less one fails instead of staying `READY`. A hung or crashing parser takes down only its own process, and a parse cut off by its timeout can't save partial text. Failures no worker observes are still open for the reconciler: a hard time limit (handled in the parent, so `on_failure` doesn't run), a `WorkerLostError` requeued forever, a retry whose publish fails and is dropped, and `on_failure`'s own write failing (logged; the document stays as it was). Accepted costs: one interpreter start per PDF (0.07–0.3 s); a swap retry pays for the embeddings again; the memory cap is sized from measurements (about 330 MiB idle plus 545 MiB per concurrent extraction at the 25 MB upload cap) and must be raised with the concurrency; an OOM kill that hits a pool child instead of the parse is a `WorkerLostError` and belongs to the reconciler's attempt budget. Another accepted edge: if run A's last transient failure lands while a concurrent run B parses the same file fine, B's `READY` finds `FAILED` and is dropped, and a re-index recovers it. The child's isolated start was checked once in a built image; `make ci` runs it only against the local install. **Rejected: retrying everything.** The reasons still need the phase, and a certain failure would take about 3.5 min for a corrupt PDF and 11.5 min for a timeout. **Rejected: an exception allowlist** (pypdf's set is open) and a broad `except` per task body (it misses code outside it). **Rejected: bounding the parse in-process**, by catching the soft limit, wrapping billiard's signal handler, or checking the clock afterwards. pypdf swallows the signal, the wrapper couples us to billiard internals, and the clock check races at the boundary. **Rejected: a per-process limit (`setrlimit`) in the child.** It turns exhaustion into a `MemoryError`, which pypdf's broad `except` sites can swallow like the soft limit, and making it uncatchable needs a bespoke interpreter hook. (The first reason given, that `make ci` couldn't test it on macOS, was wrong: the suite's testcontainers run a Linux kernel.) **Rejected: the cap with every signal as the file's fault**, which fails an innocent document for good when a neighbour's parse filled the memory. **Rejected: `SELECT … FOR UPDATE` plus a Python check** (more round trips, easy to forget on one path) and `FAILED` from any status but `INDEXED` (it overwrote a concurrent run's `READY`). **Rejected: the exception message as the reason**, which leaks file paths and provider text and isn't stable. **Rejected: stripping unstorable characters** (glues words together) or failing the document over one bad glyph. **Rejected: a `strip()` check in extraction**, a second definition of "no text" that disagrees with the chunker on zero-width spaces.
