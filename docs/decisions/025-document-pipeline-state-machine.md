# 025. The Document Pipeline Is a Guarded State Machine; the Phase Decides Retries
Status: Accepted | Date: 2026-10-24 | Amended 2026-10-25 (an OOM kill is an attempt), 2026-11-03 (every provider 4xx is transient; text past the upload cap is `extraction_too_large`) | Rewritten 2026-11-03 for the work-queue runner (ADR-027), which replaced Celery's retries and `on_failure`; the state machine, the guarded writes and the phase's retry rule are this ADR's

## Context
An upload moves `PENDING` → `PROCESSING` (`extract_text`) → `READY` → `INDEXED` (`embed_chunks`), and the pipeline's requirement is that every upload ends `INDEXED` or `FAILED` without operator action. Before this decision, many failures a worker could see left a document non-terminal for good: an uncaught exception failed the Celery task with its message acked and the status unchanged. pypdf raises an open set of exceptions beyond `PdfReadError` (`KeyError`, `ValueError`, `LimitReachedError`…): 18 % of 3,000 byte-mutated PDFs on 6.10.2, still 0.5 % on 6.21.2. A scanned PDF or a whitespace-only file chunked to nothing and stayed `READY`. A NUL or a lone surrogate in pypdf's output failed at the save. Extraction wrote `FAILED` before every retry, so a document that might still succeed already read as failed, and `FAILED` never said why. Every status write was an unconditional update of a row read earlier, so a losing concurrent run's `FAILED` could overwrite a winner's `INDEXED`. Concurrent runs were rare then, but any recovery that re-runs work (Celery's redelivery then, an expired lease now) makes them possible. Two facts ruled out bounding the parse in-process: Celery's soft time limit is a plain `Exception` raised from a signal handler, and pypdf's broad `except` sites swallowed it in 15 of 300 probes on 6.21.2, 3 of them returning text with about 2.5 k characters missing.

## Decision
**Guarded transitions.** The workers' status writes form a table in `src/domain/documents.py`. Each entry is a `Transition(to, allowed_from)`, applied as one `UPDATE … WHERE status IN (allowed_from)` (`src/workers/transitions.py`). An UPDATE that waited on a concurrent writer's row lock re-checks its `WHERE` against the committed row, so the check and the write are one step. Extraction claims from `PENDING`/`PROCESSING`, saves `READY` from `PROCESSING` and fails from `PENDING`/`PROCESSING`. Embedding claims and fails only from `READY`. The chunk swap sets `INDEXED` from any status, under the row lock. So each phase fails only the stage it owns, no run starts on `FAILED`, and a run already under way may still finish `INDEXED`: a success beats a failure. **The phase decides retries, not the exception type** (`src/workers/pipeline.py`). Pure phases (parsing bytes already read, chunking stored text) raise `PermanentFailure(reason)`, and the runner writes `FAILED(reason)` at once. Everything that touches the outside world (file, database, embedding API) is transient: the runner (`src/workers/runner.py`, ADR-027) gives the document a full-jitter backoff, doubling from 30 s (extraction) or 60 s (embedding) and capped at 10 minutes, and claims it again, up to `PIPELINE_MAX_ATTEMPTS` (5) per phase. Between attempts the document keeps its status. The attempt that uses up the budget writes the phase's `FAILED` with the reason its failure maps to: `embedding_failed` for the provider, `extraction_too_large` for a killed parse, `internal_error` for anything else. An attempt past its timeout is `extraction_timeout` at once for extraction (the same file runs out again) and transient for embedding (the provider's slow spell). The embedding provider's 4xx is transient too, 400 included: Gemini answers an invalid key with 400 `API_KEY_INVALID`, and with chunks bounded (ADR-031) no 400 is about one document's content, so each is config that fails every document alike, and failing it at once would fail the whole queue before an operator fixes it. **Reasons.** `failure_reason` is a nullable enum column with a CHECK that allows it only on `FAILED`, and the swap clears it. Four reasons are the file's (another upload can fix them): `no_text`, `unreadable_file`, `extraction_timeout`, `extraction_too_large`. Three are ours: `embedding_failed`, `internal_error`, and `interrupted` (ADR-027: the attempts all ended unrecorded). REST and MCP expose the reason, and `read_document` gives each reason its own detail. **The PDF parse runs in a child process**, `src/workers/pdf_text.py`. It runs by path under `python -I`, because the image puts `src` on `PYTHONPATH`, which `-I` ignores. The parent reads the file (I/O, transient) and pipes the bytes in. Exit 0 means text. The child's parse-failed code, or a crash (death by a signal other than SIGKILL), means `unreadable_file`: the same bytes repeat it. A kill at `PIPELINE_EXTRACT_PARSE_TIMEOUT` means `extraction_timeout`. Any other SIGKILL is the OOM killer under the extract container's memory cap (`mem_limit` = `memswap_limit`, so it kills instead of swapping). Its victim is the biggest process at that instant, which depends on what else is parsing, so it is an attempt, not a verdict: `ParseKilled` is transient, and a parse killed on every attempt ends `extraction_too_large`. So does text past the upload cap (`MAX_UPLOAD_SIZE_MB`, as UTF-8): a small compressed PDF can extract to far more text than any upload, so the child counts page by page, stops at the page that passes the cap and exits `TOO_LARGE`, failing at once, since the same file always gives the same text. This is how production parsers are bounded: a kill plus an attempt count. Any other exit (e.g. a broken deploy) is transient, then `internal_error`. A settings validator keeps parse timeout < attempt timeout < lease. The child replaces NUL and unpaired surrogates with U+FFFD, using a UTF-16 `surrogatepass` round trip that rejoins a character pypdf split into two halves. "No text" means the chunker returned no chunks, decided in `embed_chunks`. Tests: the transitions in `tests/integration/test_work_queue.py` (claims and outcome writes), `test_jobs.py` (the jobs' writes, racing swaps) and `test_runner.py` (a loser's failure never overwrites a winner's `INDEXED`); retries and reasons in `test_runner.py` (how an attempt ends, its timeout), `test_jobs.py` (which failures are permanent, provider errors), `test_document_repository.py` (the CHECK), `tests/unit/test_document_service.py` and `tests/api/test_documents.py` (each reason's detail); the child in `tests/unit/test_pdf_text.py` and `test_jobs.py`; the memory cap in `tests/integration/test_extract_memory_cap.py` (a Linux container) and `tests/unit/test_compose.py`; the settings' order in `tests/unit/test_config.py`.

## Consequences
Every failure a worker observes ends terminal, with a reason a client can act on; a failure no worker observes (a kill, a lost database) is the lease's, and a crash loop ends `interrupted` (ADR-027). A corrupt file fails in one attempt instead of five, and a text-less one fails instead of staying `READY`. A hung or crashing parser takes down only its own process, and a parse cut off by its timeout can't save partial text. Accepted costs: one interpreter start per PDF (0.07–0.3 s); a swap retried after the provider answered pays for the embeddings again; the memory cap is sized from measurements in the built image (183 MiB for the idle worker plus 543 MiB per concurrent extraction at the 25 MB upload cap; `docker-compose.yml`, checked by `tests/unit/test_compose.py`) and must be raised with the concurrency; an OOM kill that takes the worker itself instead of a parse is an unrecorded end, whose attempt the next claim counts. Another accepted edge: outcome writes aren't fenced by the lease (ADR-027), so if a late run's permanent failure lands while a concurrent run finishes extraction, that run's `READY` finds `FAILED` and is dropped with its text, and the document needs a new upload (a re-index only re-embeds documents with text, ADR-030). `tests/compose` runs the child's isolated start in the built image. **Rejected: retrying everything.** The reasons still need the phase, and a certain failure would wait out every backoff (up to 7.5 minutes for a corrupt PDF; a timeout, four more parse timeouts besides). **Rejected: an exception allowlist** (pypdf's set is open) and a broad `except` per job body (it misses code outside it). **Rejected: bounding the parse in-process.** Under Celery, pypdf swallowed the soft limit, a wrapper around billiard's signal handler coupled us to its internals, and a clock check afterwards raced at the boundary; under the runner, a parse in the event loop would block the asyncio timer meant to bound it. **Rejected: a per-process limit (`setrlimit`) in the child.** It turns exhaustion into a `MemoryError`, which pypdf's broad `except` sites can swallow like the soft limit, and making it uncatchable needs a bespoke interpreter hook. **Rejected: the cap with every signal as the file's fault**, which fails an innocent document for good when a neighbour's parse filled the memory. **Rejected: `SELECT … FOR UPDATE` plus a Python check** (more round trips, easy to forget on one path) and `FAILED` from any status but `INDEXED` (it overwrote a concurrent run's `READY`). **Rejected: the exception message as the reason**, which leaks file paths and provider text and isn't stable. **Rejected: stripping unstorable characters** (glues words together) or failing the document over one bad glyph. **Rejected: a `strip()` check in extraction**, a second definition of "no text" that disagrees with the chunker on zero-width spaces.
