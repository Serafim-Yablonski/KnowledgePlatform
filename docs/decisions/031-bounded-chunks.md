# 031. Bounded Chunks from semantic-text-splitter; Markdown Sections Never Mixed
Status: Accepted | Date: 2026-11-03

## Context
Chunk size had no upper bound. The hand-written chunkers packed paragraphs, sentences or words up to 512 cl100k tokens and then prepended up to 50 overlap tokens, so chunks routinely reached about 560 tokens. A long paragraph among shorter ones, a run with no break (base64, minified code), a code block or a table produced chunks of 3,600 to 6,000 tokens. The embedding model reads only the first 2,048 tokens of its input (ADR-022), so the rest of an oversized chunk could never be found. One such chunk also costs a client thousands of tokens of context. The chunkers also rejoined segments with spaces, losing line breaks, and treated `## ` inside a code fence as a heading. The 512-token target itself, the task type sent to the embedding model and `min_score` stay unjustified until a retrieval eval exists (ADR-024). This decision is about correctness only.

## Decision
**Every chunk, overlap included, is at most `max_tokens` (512) cl100k tokens. Chunks are the input's own text in order, and no non-whitespace character is lost.** The splitting is `semantic-text-splitter` 0.33.1 (Rust, maintained), bounded by the tiktoken `gpt-4` tokenizer, which is cl100k, the encoding `count_tokens` uses. Both count ordinary tokens: a document quoting a reserved string such as `<|endoftext|>` holds text, which tiktoken's `encode` would reject. Plain text and PDF text use `TextSplitter`, which splits at the largest boundary that fits: paragraph, line, sentence, word, and characters last. Markdown is cut into sections first by our own scan: CommonMark ATX headings `##` and `###` outside fenced code blocks, where a fence closes only on a line of its own character at least as long. Each section, heading line included, is split by `MarkdownSplitter`, which keeps blocks such as code blocks whole when they fit. A chunk never spans two sections, so its `section` path is exact. A heading with nothing under it joins the next section. Tests in `tests/unit/test_chunking.py`: property-based tests with Hypothesis over generated documents built from the inputs that broke the old chunkers (the bound, and "in order, verbatim, nothing lost", at 32 and 512 tokens), plus examples for sections, fences and the overlap at seams.

## Consequences
Every stored chunk is now embedded whole. A `read_document` page is at most 20 × 512 cl100k tokens, but cl100k only approximates other models' tokenizers. Headings are now part of chunk text, so reading the chunks in order reads the document. Small markdown sections become small chunks, as before; a section is never padded with its neighbour. Existing chunks change only on `make reindex` (ADR-030), and stored `chunk_index` citations go stale then, which is acceptable without users. **Rejected: fixing the hand-written chunkers.** That needs four separate fixes (re-splitting oversized segments, a hard token split last, keeping the original separators, fence-aware headings), all code we would maintain to match a library's tested behaviour. **Rejected: `MarkdownSplitter` over the whole document.** It packs short sections together, and such a chunk can be labelled with only one of their headings.
