# 029. Exact Vector Search, Narrowed to the Workspace First
Status: Accepted | Date: 2026-11-03 | Supersedes ADR-014

## Context
ADR-014 chose an HNSW index for search. EXPLAIN showed that no search ever used it (PostgreSQL 18.3, pgvector 0.8.2, 40,000 chunks across 20 workspaces). An HNSW scan serves only `ORDER BY embedding <=> q LIMIT k`, and our query ranked by `1 - distance` from a CTE. The same plan showed a worse cost. PostgreSQL pushed the `similarity_score >= min_score` filter into the chunk scan, so every search computed the distance for every chunk of every workspace before the join kept one workspace's rows (132 ms warm). Computed only for that workspace's 2,000 chunks, the same search took 9 ms. Using the index would not have been correct either. pgvector applies a `WHERE` filter after an approximate index scan, so a shared index first collects the nearest chunks of all workspaces (`ef_search`, 40 by default) and then discards the other workspaces'. In the probe, a top-5 search for a workspace holding 5% of the chunks returned 1 row. pgvector's README says the same: "sharing an approximate index between tenants means vectors from one tenant can affect recall (and speed) for other tenants. For tenant isolation, use list partitioning or separate tables."

## Decision
**Search is exact over the workspace's chunks, and `document_chunks.embedding` has no vector index.** `SIMILAR_CHUNKS_SQL` (`src/repositories/search.py`) joins chunks to the workspace's `INDEXED` documents, ranks by similarity and takes the top k. It then applies `min_score` outside the `LIMIT`. This returns the same rows, because they are ranked by that same score, but a filter inside the `LIMIT` would be pushed into the chunk scan. Migration `c0d1e2f3a4b5` drops `ix_chunks_embedding_hnsw`. Tests in `tests/integration/test_search_repository.py`:
- A workspace gets its true top k even when another workspace holds 2,000 closer chunks. With planner statistics in place, this fails against a shared HNSW index, with or without iterative scan.
- No plan node that reads `document_chunks` evaluates the distance (EXPLAIN). This fails if the score filter sits beside the workspace filter.

## Consequences
Every search has perfect recall, and its cost grows with the size of its own workspace, not with all tenants' data. From the 9 ms per 2,000 chunks measured here, 100,000 chunks would take about half a second (an extrapolation, not measured). Inserts no longer maintain a graph. When one workspace's search becomes too slow, the next step is list partitioning of `document_chunks` by workspace (a `workspace_id` column on chunks first) with an HNSW index per partition: each index then holds one tenant's vectors, so no filter discards results. **Rejected: a shared HNSW index with `hnsw.iterative_scan`.** Results are approximate (`relaxed_order` may return them out of order), it stops at `hnsw.max_scan_tuples` (20,000), it needs `ef_search` tuning, and one tenant's vectors still affect another's recall and speed. **Rejected: correcting only the documentation.** Every search would still compute the distance for every chunk in the table. **Rejected: IVFFlat**, which has the same post-filter loss and also needs a training step (ADR-014).
