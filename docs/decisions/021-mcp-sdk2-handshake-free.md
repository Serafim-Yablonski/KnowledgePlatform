# 021. MCP on SDK 2.x, Handshake-Free Protocol Only
Status: Accepted, supersedes ADR-013 (session state; its API-key decision stands), amends ADR-012 | Date: 2026-10-19, revised 2026-10-23

## Context
On `mcp` 1.x the server was stateful: the SDK spawned a session task during `initialize` that copied that request's ContextVars, so tools saw the user who opened the session forever (cross-user identity bug), and sessions lived in process memory. MCP revision 2026-07-28 removes the `initialize` handshake and sessions — every request is a self-contained POST carrying its version in `MCP-Protocol-Version` and `params._meta` — and `mcp` 2.x implements it. But 2.3.0 routes on that header alone (its own `TODO(L49)` calls this temporary): a request without it, or with a handshake-era version, still takes a stateful legacy path, with no switch to turn it off. The spec makes refusing those clients its own rule: every POST MUST carry the header, a server that doesn't serve header-less clients MUST reject them (400 `HeaderMismatch`), an unsupported version gets 400 `UnsupportedProtocolVersion` listing what is supported, and a revision-only server SHOULD answer GET/DELETE with 405. Two more SDK facts shaped the design: a tool exception other than `ToolError` reaches the model only as `Error executing tool <name>`, and the SDK's DNS-rebinding guard can't check Origin without also checking Host against an exact allowlist, and runs after our middleware.

## Decision
`mcp==2.3.0`. `MCPServer`'s session-manager handler is served at an exact `Route("/mcp")` behind `MCPAuthMiddleware`, which checks, in order: any `Origin` → 403 — we serve no browser clients, and the spec requires Origin validation against DNS rebinding; the attack barely applies (a browser never attaches our bearer token by itself), so this is spec compliance, kept in case ambient credentials ever appear, and it runs first so no 401 or 400 answers a request the spec says gets 403; then the protocol guard, which mirrors the SDK's header-only routing rule — non-POST → 405 `Allow: POST`, missing header → 400 `HeaderMismatch`, handshake-era version → 400 from the SDK's `unsupported_protocol_version_rejection()`, everything else passes untouched, so newer revisions arrive with an SDK upgrade (no version literal in `src/`); then bearer auth (JWT or API key, 401 with `WWW-Authenticate`), storing the user in the request's ASGI `state`, which tools read from their own request via `ctx.request_context.request`. The guard is to be deleted once the SDK can refuse handshake-era clients itself (an SDK upgrade must re-check its release notes; no test can detect it); until then `test_handshake_era_version_is_unsupported` and `test_unknown_newer_version_is_left_to_the_sdk` pin the guard's rule — handshake-era refused with the spec's error, anything else left to the SDK. The SDK's own DNS-rebinding guard is explicitly off. Tools register through `_add_tool`, which turns an `AppError` into a `ToolError` with its `detail` (the text REST already shows the same user; a rate limit adds its retry time); any other exception stays opaque. Pinned by `tests/integration/test_mcp_protocol.py` (real SDK client over ASGI: per-request identity, refusals, Origin order, 401s) and `tests/unit/test_mcp_tools.py` (error texts, unchanged schemas); verified end to end with Claude Code 2.1.302 against the Docker stack.

## Consequences
No sessions remain anywhere: identity follows each request, and the legacy path is unreachable. The cost is reach: only clients speaking 2026-07-28 or later connect, and in October 2026 client support was still uneven — accepted because adoption is rising and the handshake is deprecated; `scripts/generate_mcp_config.py` lists only verified clients. **Rejected: staying on 1.x** and hand-writing stateless behaviour into it. **Rejected: serving older clients** (via `stateless_http`, the legacy path, or a bridge such as `mcp-remote --protocol auto`) — not for identity: probed on 2.3.0 with our middleware, the legacy path gives each call its own request's user, since the SDK runs every message in its sender's context. The reason is one protocol and no session state to own: legacy sessions live in process memory (a session cap, sticky routing across replicas), and they would need binding to their user through the SDK's own auth types — unbound, anyone holding a session id can use or `DELETE` it. **Rejected: the SDK's native Host/Origin guard**: it can't check Origin without an exact Host allowlist whose misconfiguration answers 421 for the real hostname, and, running after our middleware, it lets 401/400 answer first; its own maintainer's TODO questions whether it should exist. **Rejected: `ServerMiddleware` for error translation**: it only sees the already-generic result. **Rejected: `AppError` subclassing `ToolError`**: services would import the SDK. **Rejected: the SDK's `get_access_token()`**: a ContextVar that also requires OAuth settings, which are out of scope.
