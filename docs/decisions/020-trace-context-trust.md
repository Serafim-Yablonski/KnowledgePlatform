# 020. Trace Context Comes Only from Our Own API
Status: Accepted, amends ADR-006 | Date: 2026-10-19, amended 2026-10-20 (REST instrumentation, Logfire 5), amended 2026-11-02 (ADR-027: no broker; workers trust no incoming context and continue the one our API stored in the row), amended 2026-11-03 (no baggage)

## Context
A caller can send a W3C `traceparent`: REST as an HTTP header, MCP inside each request's `_meta`, where the SDK's default-on `OpenTelemetryMiddleware` parents its span on it. Both are read through the global propagator, which Logfire installs, and Logfire's default (`distributed_tracing=None`) adopts the caller's context and warns once. Probes showed what that means for us: with a sampled context our span joins the caller's trace id, and with an unsampled one (`…-00`) our span is not recorded at all, because the default sampler follows the parent — any client could hide its own requests from our traces. A second probe found that `src/workers/celery_app.py` ran `logfire.configure()` and `setup_logging()` at import; the API imports that module lazily (health check, task enqueueing), so the first such request reset the API's configuration. In workers the import-time logging setup was also discarded, since Celery clears the root logger's handlers unless a `setup_logging` receiver is connected (`celery/app/log.py`). A later review found REST had no server spans at all: `instrument_fastapi` ran in `lifespan`, after Starlette built its middleware stack on the lifespan's own ASGI call — so REST's `traceparent` was "ignored" only because nothing read it, and REST-enqueued tasks started traces of their own. asyncpg was never traced either: its instrumentation package wasn't installed, and a `try/except` turned that into a startup warning.

## Decision
`configure_logfire(..., trust_incoming_trace_context)` in `src/core/observability.py` is the one place any process configures Logfire; `instrument_libraries()` (asyncpg, httpx, from `logfire[...]` extras, failing loudly if missing) is the one set the API and the workers trace; `instrument_app()` instruments FastAPI in `create_app`, before the app serves anything, and spans record once startup configures Logfire. The API passes `False` (`setup_observability`): REST and MCP callers are untrusted, so their trace context is ignored and every span records under our own trace id. *(Amended 2026-11-03.)* "Trace context" includes W3C baggage: Logfire's no-extract wrapper resets only the parent span, and by default copies baggage onto every span as attributes, so a client's `baggage` header became attributes on our spans and rode the stored context onto every worker attempt. `configure_logfire` installs the W3C trace-context propagator alone before Logfire wraps it; we set no baggage ourselves. *(Amended 2026-11-02.)* Workers pass `False` too: no request reaches them, and each attempt's span starts under the trace context our API stored in the document row (`trace_context`, written by `create` inside spans it started; ADR-027), so one trace still follows an upload to its end. A worker's logging and tracing are set up by `configure_process` in `src/workers/__main__.py`, which only the entry point calls, never an import. (Under Celery, workers passed `True`, since task context came only from our API through the broker, and were set up from Celery's `setup_logging` and `worker_process_init` signals.) Pinned by `tests/unit/test_observability.py` (each scenario in a fresh interpreter, since this state is process-global, and with `LOGFIRE_TOKEN` emptied so nothing exports: the API ignores context over MCP `_meta` and REST, and a client's baggage, a worker adopts none, importing the worker configures nothing, the API and the workers trace the same libraries), by `tests/integration/test_runner.py`'s trace tests (an attempt continues the upload's trace, and a failure as interrupted ends it), by `test_rest_requests_are_traced_after_startup` (the real `create_app()` and lifespan), and by `filterwarnings = error:Found propagated trace context` in `pyproject.toml`: that REST test sends a `traceparent` in-process, so anything reconfiguring Logfire's trusting default in the test process fails it.

## Consequences
Our trace ids and sampling are ours, API → worker traces stay linked, and importing worker modules is free of side effects. A client running its own distributed tracing can no longer see our spans inside its trace; nothing needs that today. **Rejected: Logfire's default, or `distributed_tracing=True`**: either lets the caller choose our trace ids and switch recording off; `True` only hides the warning. **Rejected: removing the SDK's tracing middleware, filtering its tracer, or stripping `traceparent` from `_meta`**: loses useful native spans or hand-writes a filter, and leaves REST's header exposed. **Rejected: `add_baggage_to_attributes=False` alone**: the baggage would still be stored with each upload and forwarded on our outbound calls. **Rejected: recording the caller's context as a span link**: keeps the correlation without trusting it, deferred until someone needs it. **Rejected: a `filterwarnings` ignore for the warning**: it would hide the cause. **Rejected: rebuilding the middleware stack in `lifespan`** (`app.middleware_stack = None`): relies on Starlette internals. **Rejected: Logfire's `ignore_no_config` setting** for its "instrumenting before configure" warning: process-wide, it would also hide a worker that never configures; the warning is filtered only around `instrument_fastapi`.
