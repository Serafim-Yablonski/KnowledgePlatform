# 028. Health Is the API's Readiness; Pipeline Lag Is Information
Status: Accepted | Date: 2026-11-02 | Amends the health checks of ADR-026; follows ADR-027

## Context
Under Celery, `/health` answered 503 unless the database, the cache, the broker and a Celery ping all succeeded. The ping tied the API's status to the workers: CI's smoke step, which runs no worker, had to accept a 503 and check fields one by one. ADR-027 removes the broker and Celery, so neither can be checked, and a worker has no port to probe. Postgres holds what is left to measure. A document is *due* when its status is owed work and its `available_at` has passed: no claim holds it and no backoff hides it. How long the oldest due row has waited answers "is the pipeline keeping up?" whatever the number of workers. It also catches dead workers, stuck ones and too few slots, which a liveness probe of each worker would not.

## Decision
**The status code reports the API's own readiness: the database and the cache, nothing else.** The body adds `pipeline: {extract_lag_s, embed_lag_s}`, the seconds the oldest due row of each phase has waited, 0 when none is due. It is computed by `lag_statement(phase)` in `src/workers/queue.py` from `due(phase)`, the same predicate the claim uses, so the lag counts exactly the rows a claim would take (`tests/integration/test_work_queue.py`). Lag never changes the status code. A failed lag query reports `pipeline: "error"` beside an otherwise healthy answer. Both queries share one connection, and a database that has failed is not asked again. A connection that cannot be made, or that the server refuses (a wrong password, a missing database, the connection limit), counts as a database error. At connect, the driver's errors (the OS's `OSError`, asyncpg's `PostgresError`) arrive unwrapped by SQLAlchemy; before this, such a database crashed the endpoint with a 500 instead of a 503. Each dependency gets `PROBE_TIMEOUT_S` (3 s), so a server that never answers fails the probe instead of hanging it for asyncpg's 60 s. Tests: `tests/integration/test_health.py`.

## Consequences
A load balancer or orchestrator acting on `/health` takes an API instance out of rotation only for something that instance can fix. A backlog stays visible, but acting on it is left to whoever reads the number, as no threshold is built in. CI now asserts a 200 `healthy` with zero lag after migrating with the image's own alembic. Each `/health` call costs two indexed queries on the partial index over owed rows. **Rejected: 503 above a lag threshold.** It ties API readiness to the workers again, as the Celery ping did, and needs a threshold that would be wrong for one deployment or another. **Rejected: a heartbeat per worker** (a file or a row each worker updates). It shows a worker is alive, not that work moves, and in compose nothing restarts an unhealthy container (P5). **Rejected: dropping worker health entirely.** Nothing in the system would then show that documents have stopped moving.
