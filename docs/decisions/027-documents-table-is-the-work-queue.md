# 027. The Documents Table Is the Pipeline's Work Queue
Status: Accepted, implemented (pivot steps P2–P6, 2026-11-02; the acceptance suite, P7, is open) | Date: 2026-11-02 | Supersedes ADR-007 and the broker and worker parts of ADR-026; replaces ADR-025's Celery mechanics (autoretry, `on_failure`, the hand-off rule) but keeps its state machine and guarded writes

## Context
The pipeline's requirement is that every upload ends `INDEXED` or `FAILED` without operator action. After ADR-025 and ADR-026 the work owed was still written to two systems with no shared transaction: the document's status in Postgres and a Celery message in Redis. Every failure left open came from that split, or from Celery deciding alone when a message is done. A publish that fails after the commit leaves a `PENDING` or `READY` row that no message will ever wake. A hard time limit acks the message and runs no `on_failure`. `on_failure`'s own write can fail. A host crash loses the last second of the AOF. A worker that dies is redelivered at once (`task_reject_on_worker_lost`, which Celery's docs warn "can cause message loops") or after the one-hour visibility timeout. The planned fix was a reconciler: a beat-triggered sweep that requeues silent documents, plus an attempt counter in the row, because a requeue is a new message whose Celery retry count starts at zero. That adds a scheduler and a second recovery path next to Celery's own. The document row already records what is owed (`PENDING`/`PROCESSING` owe extraction, `READY` owes embedding), and the PostgreSQL docs name `FOR UPDATE SKIP LOCKED` for "multiple consumers accessing a queue-like table": the pattern behind Solid Queue (Rails 8's default job backend), Oban, graphile-worker and River.

## Decision
**Workers claim documents from Postgres; nothing else carries the work.** Two columns: `attempts` and `available_at`, with a partial index on `available_at` over the owed statuses. A claim is one short transaction: it locks the oldest owed row whose `available_at` has passed, skipping rows other claims hold, adds 1 to `attempts`, sets `available_at` to now plus the phase's lease, and commits before any work starts. The lease is the recovery mechanism. A worker that is killed, runs out of memory or loses its host leaves a lease that expires, and the next claim takes the row and counts the attempt. The lease is longer than the phase's attempt timeout (`asyncio.timeout`; the PDF child keeps its own kill), so a live attempt never loses its row. A permanent failure writes `FAILED(reason)` at once. A transient one sets `available_at` to a full-jitter backoff, or writes `FAILED` with the phase's reason when the budget (5 attempts per phase) is used up. A claim that finds the budget used up by attempts that ended unrecorded writes `FAILED(interrupted)`. Finishing extraction resets `attempts`. Each phase runs as its own service from one image (`python -m src.workers extract` / `embed`), async on asyncpg. One claimer per process fills its slots and polls about once a second while nothing is owed; a stop ends claiming, gives running attempts a grace period, then cancels their jobs and releases their rows. An upload only commits its `PENDING` row, together with its trace context (`trace_context`): each attempt's span starts under it, so one trace follows an upload to `INDEXED` or `FAILED`, as Celery's message headers did. Every write stays guarded as in ADR-025, so a worker that outlives its lease cannot undo a newer outcome, and a repeated embedding only replaces the chunk set with an equal one.

## Consequences
One mechanism replaces Celery's acks, redelivery, autoretry and `on_failure`, the visibility timeout, the planned reconciler and its beat. No failure leaves a document owed but unclaimable: an unrecorded end costs one attempt and one lease, and a crash loop ends `FAILED(interrupted)` after 5. Redis no longer holds work, so it goes back to a plain cache. The costs: a new upload waits up to the poll interval; an idle worker runs one indexed query per second; we lose Celery's ecosystem (events, `inspect`, Logfire's Celery integration), so attempts get spans by hand; and the worker loop (claim, outcome, shutdown) is our own code, about 250 lines (`src/workers/runner.py`). The attempt is the upload's child, not a linked trace, which holds while each owed row has one cause and its attempts are bounded (5 per phase, backoff capped at 10 minutes): whatever makes a row owed again (a future re-embed) writes its own context. **Rejected: span links**, the default of job-queue instrumentations (Sidekiq, Que, Oban), whose jobs can have many causes or retry for weeks; ours have neither, and a link would split each upload's history into separate traces. **Rejected: Celery + a reconciler.** It closes the same gaps, but keeps the dual write and adds a second recovery path and a scheduler. **Rejected: RabbitMQ.** Publisher confirms close the AOF window, but the status write and the publish still share no transaction, and Celery's ack on a hard timeout does not depend on the broker. Its delivery limit only counts redeliveries of the same message, so a requeue still needs the counter in the row. **Rejected: Procrastinate**, a Postgres queue for Python. It has no asyncpg connector, so an enqueue cannot join the API's transaction, and its job status would mirror the document's. **Rejected: fencing tokens** (writes conditioned on the claim's `attempts`). Guarded writes and the idempotent chunk swap already make a late writer harmless. **Rejected: a lease heartbeat.** The attempt timeout bounds every attempt below the lease. **Rejected: LISTEN/NOTIFY**, which cuts the wait to near zero but needs a listening connection and polling as a backstop anyway.
