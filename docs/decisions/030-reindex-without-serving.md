# 030. Re-index by Owing Embedding Again, Without Serving Old Chunks
Status: Accepted | Date: 2026-11-03 | Follows ADR-027

## Context
Stored chunks go stale when the chunking changes (C1, bounded chunk size), or when the embedding model or its task type changes. A chunking change leaves old vectors comparable with new query vectors. A model change does not, and ranking old vectors against new queries would put results in the wrong order. Every document keeps its extracted text (`raw_text`), so a re-index re-chunks and re-embeds without parsing any file again. The open question was whether search should keep serving a document's old chunks until its new ones are ready. This project has no deployment (only compose, for development and demos), so nobody is searching while a re-index runs.

## Decision
**`python -m src.workers reindex` (`make reindex`) makes every document with extracted text owed embedding again, and the embed workers do the rest.** One transaction moves every `INDEXED` or `FAILED` document whose `raw_text` is set to `READY` (`REINDEX` in `src/domain/documents.py`, `reindex` in `src/workers/queue.py`). It resets attempts to 0, sets `available_at` to now, clears `failure_reason` and stores the command's span context in `trace_context`, so one trace shows the re-index and every re-embedding. Rows already owed work keep their place: a claim holding a `READY` document keeps its lease, and those rows will be embedded by the code that is running anyway. A `FAILED` row without text never reached embedding, and only a new upload can fix it. The usual claim and chunk swap (ADR-025, ADR-027) finish each document. Tests: `tests/integration/test_work_queue.py` (the write, and the command's single trace), `tests/unit/test_worker_main.py` (the subcommand runs it), and `tests/integration/test_search_repository.py` (a `READY` document is out of search).

## Consequences
While `READY`, a document is out of search, and `read_document` answers "still being processed". A failed re-embed leaves it `FAILED` with its text, and running the command again retries it. The command must run after the new workers are up, because a worker still running old code could finish a document with the old chunking. Running the command twice embeds everything twice: no column records which chunking or model produced a chunk. One `UPDATE` locks every row it changes until it commits, which is fine at this size; a large corpus would batch it. **Rejected: keep serving during the re-index.** It needs an owed mark separate from the status, a per-document swap that keeps the old chunks if the new embedding fails, and an "embedding version" column that search filters on, so old-model vectors are never ranked against new-model queries. That pays off only with live users. **Rejected: re-extracting from the file (back to `PENDING`).** The text is already stored, so every PDF would be parsed again for nothing. **Rejected: a per-workspace re-index or an API endpoint.** No caller needs either.
