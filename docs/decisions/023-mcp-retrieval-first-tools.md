# 023. MCP Exposes Retrieval Tools, Not Answers
Status: Accepted, amends ADR-012 (MCP no longer offers `ask_question` or resources) | Date: 2026-10-23

## Context
Our MCP clients are developer tools and code agents: each already runs a capable model, its scarce resource is context, and what it lacks is our private corpus. The 1.x surface served a different client. `ask_question` had our own agent answer from a default of five retrieved chunks, so a second model answered for the first — the same retrieval, plus latency and cost, with the evidence hidden behind a paraphrase. Two resources listed documents and workspace stats, but the spec makes resources application-driven (the host decides what to attach) while tools are model-controlled, so a model working on a task could not reach them. Tools returned untyped dicts and lists, which the SDK publishes as an untyped `object` (lists wrapped as `{"result": [...]}`), and none declared its effects, so clients had to assume the spec defaults: destructive and open-world. Under 2026-07-28 the server's `instructions` travel only in the `server/discover` result, which a client that pins a version skips, and clients differ in whether their model sees them at all.

## Decision
Four read-only tools serve one loop — find the scope, locate, read around the hit, locate again, cite — and every one after the first takes `workspace_id` as an explicit, membership-checked argument: `list_workspaces` (`id`, `name`, `description`); `search_documents` (hits carry `document_id`, `document_title`, `chunk_index`, `section`, `chunk_text`, `score`); `list_documents` (newest first, cursor-paged); `read_document` (an indexed document's current-version chunks in order from `start_chunk`, with `total_chunks` and `next_start_chunk`). `ask_question` stays in REST only; resources are gone. Each tool returns a Pydantic model from `src/mcp_server/schemas.py` — MCP's own, separate from REST's schemas so neither contract moves with the other — which the SDK publishes as the output schema and sends both as structured content and, serialised, as the text block (the spec's backwards-compatibility SHOULD), so the model reads the same JSON whichever channel its client uses. Every tool registers through `_add_tool` with annotations: `read_only_hint` per tool, `open_world_hint=False` (only our corpus), `destructive_hint=False` on the one writer. Descriptions are the contract: each says what the tool does, when to prefer it over its siblings, what it returns and what to call next, naming only real tools, arguments and fields; `instructions` only summarise the retrieval loop. The research tools stay registered with their old descriptions and untyped outputs, but out of `instructions`, until Track 4 replaces them (a failed run reports `running` forever). Pinned by `test_server_exposes_only_tools` (exact tool set, no resources), `test_tools_publish_typed_output_schemas`, `test_text_and_structured_content_carry_the_same_data`, `test_every_tool_declares_its_effects`, `test_prompts_name_only_what_exists`, `test_instructions_cover_the_retrieval_loop` and `test_default_mode_client_discovers_the_server`.

## Consequences
The client's model sees the evidence itself and cites it by `document_id` and `chunk_index`; questions that need many retrievals go to research (Track 4), where returning a report instead of fifty chunks does save context. Annotations are hints, not enforcement: the spec tells clients to distrust them from untrusted servers, and a read-only hint does not skip approval prompts in every client. Whether a client's model sees the output schema varies, so descriptions repeat the output fields, at the cost of tokens in every tool listing. Track 4 must lift the research exceptions in `test_tools_publish_typed_output_schemas` and `RETRIEVAL_TOOLS`. **Rejected: a Q&A-first surface** (`ask_question` over MCP): a model answering for a model, with no context saved. **Rejected: keeping resources** next to the list tools: two ways to read the same data, one of which the model can't call. **Rejected: text-only results** (`structured_output=False`): ids and cursors must survive verbatim into the next call; JSON costs `read_document` an estimated 3–32% more tokens than plain text (tiktoken as a proxy, ADRs to markdown lists and code), accepted and cheap to revisit. **Rejected: reading `raw_text` by character offsets**: chunks store no offsets, so a search hit could not be located in it; reading by chunk accepts about 10% repeated text where neighbouring chunks overlap.
