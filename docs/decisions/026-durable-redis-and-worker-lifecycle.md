# 026. One Durable Redis for Broker and Cache; a Stopped Worker Hands Its Work Back
Status: Superseded by ADR-027 (2026-11-02: no broker, so Redis is a cache again and persists nothing; a stopped worker releases its rows) and ADR-028 (health); the restart policies still hold | Date: 2026-10-25

## Context
One Redis holds the Celery broker (the `extract` and `embed` queues and the unacknowledged messages) next to the auth cache, the rate limiter's sorted sets, API-key touch markers and research token streams. The pipeline's requirement is that every upload ends `INDEXED` or `FAILED` without operator action, and a lost broker message leaves a document waiting for the reconciler, about 1.5 h. Docker Compose is the only runtime, and it lost queued work in ordinary use. `redis:7-alpine` ran with RDB snapshots on an anonymous volume. A `docker compose down` + `up` started from an empty Redis, and a kill of the Redis process lost every write since the last snapshot, which at our write rate is up to an hour of uploads. Redis 8's image no longer declares a volume at all. Persistence (`appendonly`) and eviction (`maxmemory-policy`) are settings of the whole instance, not of a database number. Every key outside the broker gets its TTL in the same call or pipeline that writes it, so their memory is bounded by TTL × request rate, and no data needs eviction. `docker compose stop` sends SIGTERM, waits 10 s and then SIGKILLs. Celery's SIGTERM is a warm shutdown that waits for running tasks (up to 3 or 6 minutes), so the kill came first, and the message waited in `unacked` for the one-hour visibility timeout. No service had a restart policy, so a crashed or OOM-killed container stayed down. The result backend was configured, but nothing ever stored or read a result.

## Decision
**One Redis 8 instance, durable and never evicting.** It runs `redis-server --appendonly yes --appendfsync everysec --maxmemory-policy noeviction` on a named volume, `redis_data:/data`, with no `maxmemory`. The roles stay separate in configuration, `CELERY_BROKER_URL` for the broker and `REDIS_URL` for the cache and the rate limiter, so a deployment can split them with env vars alone. The result backend is gone. `/health` reports `cache` (the app's client) and `broker` (one connection to `CELERY_BROKER_URL`) separately. **Every service restarts by itself** (`restart: unless-stopped`). **A stopped worker hands its work back.** Workers run with `REMAP_SIGTERM=SIGQUIT` and `worker_soft_shutdown_timeout` (`CELERY_WORKER_SOFT_SHUTDOWN_TIMEOUT`, 20 s) inside `stop_grace_period: 30s`. On a stop, running tasks get 20 s to finish; whatever still runs is cancelled and its message goes back to the queue at once, with no `on_failure`. Tests start Redis with the image and command read from `docker-compose.yml`, so they test what compose runs. Pinned by:
- durability: `test_a_published_task_survives_a_kill_of_redis`, `test_redis_keeps_its_data_in_a_named_volume`, `test_redis_never_evicts`, `test_no_result_backend`, `test_health_checks_the_broker`;
- lifecycle: `test_every_service_restarts_after_a_crash`, `test_workers_turn_sigterm_into_a_soft_shutdown`, `test_the_soft_shutdown_ends_inside_the_grace_period`, `test_worker_soft_shutdown_timeout`, `test_a_stopped_worker_puts_its_running_task_back` and `test_a_task_that_ends_within_the_soft_timeout_finishes` (a real worker process on a real Redis).

## Consequences
A message Redis acknowledged survives a kill of Redis, a container recreate and a `down` + `up`. Only `down -v` empties the queue, on purpose. A crash of the whole host can still lose about the last second of publishes, and the reconciler recovers those documents. A stop costs the work of tasks cut off after 20 s: they run again from the start, which is safe because both pipeline tasks are idempotent and costs at most one repeated embedding call. A stack left running comes back after Docker restarts. The cache is persisted too. That is harmless except after a database-only wipe, when cached API keys and memberships answer for up to their 300 s TTL. CI's service Redis can't take a `command`, so it isn't durable; it only backs the image start-up check. **Split into two instances** when the first data that needs eviction arrives (for example the search-result cache ADR-016 describes, which was never built), or when broker and cache need separate scaling. **Rejected: two Redis services now.** The textbook shape, but the cache needs no eviction policy, so a second instance buys only a non-persisted cache, and one more container, CI service and health check. **Rejected: one instance with `volatile-lru`.** It rests on an invariant nothing enforces (every cache key has a TTL and no broker key does), and it would persist every rate-limit hit to the AOF anyway. **Rejected: separate database numbers**, which isolate keys but not persistence or eviction. **Rejected: RabbitMQ**, Celery's recommended durable broker. It is a new service, it would void the kombu-Redis failure facts the pipeline's tests were built on, and it removes no need for the reconciler, because the status write and the publish still share no transaction. **Rejected: `appendfsync always`** (a host crash is the reconciler's case) and tighter RDB snapshots (a fork per write, still a loss window). **Rejected: a grace period as long as the hard time limit**, which would make every `docker compose down` take six minutes.
